# DRAFT — Website or web application: which does your business need?

**Owner review required before publication.** Drafted 20 October 2026 from current service pages and original portfolio records. Confirm the project descriptions and package scope before posting. This is not a live route.

Start with the visitor's job. If people mainly need to **understand your offer and contact you**, a business website is often the right first build. If they must **sign in, enter data, track a process or work through a recurring task**, you are describing a web application. A project can contain both: a public website for discovery and a private app for the workflow.

| Question | Business website | Web application |
|---|---|---|
| Main visitor action | Read, compare, inquire or purchase through a defined storefront. | Complete repeated tasks, manage records or collaborate inside a workflow. |
| Typical content | Services, proof, FAQs, contact and policies. | Roles, states, forms, dashboards, records and permissions. |
| Scope conversation | Pages, content, design, contact path and launch. | Users, minimum features, data, integrations, edge cases and ongoing support. |
| Main risk if underspecified | Missing content or an unclear route to inquiry. | A growing feature list that never produces a focused usable first version. |

## A useful way to decide

Write one sentence beginning, “A visitor needs to…” If it ends with “see what we do and send a brief,” plan the website first. If it ends with “log in each week to update tasks and see invoice status,” map the application workflow. Do not buy or build a dashboard merely because competitors have one.

For an app, define the **minimum usable workflow** before asking for a fixed price: who uses it, what they enter, what the system does, and what result they need to see. Separate must-haves from later ideas. An MVP is a deliberately limited first version, not a promise that every future feature is cheap or included.
